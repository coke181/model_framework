### 内存仓储结果如何理解

- 小数据集下，64 增至 128 并发没有提高吞吐，却恶化客户端尾延迟。业务队列和接口处理时间远短于完整请求耗时；尚未完全测量的部分包括异步调度和响应准备。不能因此断定业务逻辑或网络栈中某一处是瓶颈。
- 不应声称真实服务可承载 1.4 万 QPS，也不应凭此逐个优化仓储函数：客户端与服务同机，存储和数据规模均不具代表性。Tracy 墙钟区间包含锁和 I/O 等等待，WPR 的采样权重不是毫秒。
- 后续需将压测客户端移到另一台机器，预热后做开放环速率扫描，至少覆盖 1/8/32/64/128 并发及更长持续时间；记录目标速率、实际完成速率、2xx/429/503、客户端与服务端 P50/P95/P99、CPU、主机规格和业务比例。
- 为真实存储压测创建**可丢弃**的本地 MySQL 和 Redis 数据集，预置代表性的玩家、好友、消息、邮箱及商品；除读接口外纳入登录、聊天写入、邮件领取和库存变更。现有脚本会注册用户和发邮件，绝不可直接用于开发或生产数据。

测试结束后临时进程已关闭；可丢弃的数据目录保留在磁盘，便于复测。

## 更高吞吐、更低延迟：按证据实施

1. **先定义目标，复测真实负载。** 明确目标并发、接口比例、P99 上限及错误率；分机压测，固定构建和配置，预热后重复多轮开放环速率扫描。预置不同账号规模、好友关系、聊天记录和邮箱大小。记录目标与完成速率，防止压测端过载造成错误的“低延迟”结论。
2. **拆分端到端耗时。** 分别采集请求排队、业务执行、MySQL 连接池等待与 SQL 执行、Redis 调用、响应写回的 P50/P95/P99 和调用次数；同时观察 CPU、线程数、队列深度/拒绝数、MySQL 慢查询及 `EXPLAIN`、Redis 命令数/延迟。真实存储下 `/friends` 的客户端 P95 约 36-39 ms、业务队列 P95 约 12-13 ms，当前证据还不足以指认队列增长的根因。
3. **针对实测瓶颈改动。** SQL 慢就先核查过滤和排序索引、扫描行数与执行计划，再考虑分页、避免重复查询和减少数据库往返；Redis 调用多就评估批量或流水线，但要保持一致性语义；排队 P99 高就检查工作线程是否阻塞于数据库、锁、日志，以及队列边界和过载时 429/503 的背压行为。只有池等待持续主导尾延迟，才继续调连接数；现有 8→16 实验没有吞吐收益。
4. **补并发写入和正确性测试。** 在独立数据集上并发执行邮件领取、背包变更、聊天发送和登录/会话更新，记录吞吐、P99、超时及错误；同时核验不重复领取、不丢库存更新、不重复或乱序写消息。已有的串行各 50 次写入不足以证明高并发能力。
5. **前后对照与稳态验证。** 每次只改一个因素，保持数据集、请求比例、主机和构建选项不变，多轮对照吞吐、P95/P99、错误率、CPU、队列和数据库资源。先找到可持续的最大请求率，再做 10-30 分钟稳态与更长时间的内存、连接数增长检查；区分 Tracy/采样开销和发布构建性能。

当前优先级是第 1、2、4 步；没有证据支持直接增加线程、盲目扩容 MySQL 连接池，或把内存模式的 1.4 万次/秒写成真实容量。

## 本机登录极限吞吐模式

本机若只测试 HTTP、密码校验和 MySQL 账号读取，可以使用以下开发环境变量：

```powershell
$env:HELLO_SERVICE_STORAGE_MODE = "mysql_redis"
$env:HELLO_SERVICE_IN_MEMORY_SESSIONS = "1"
$env:HELLO_SERVICE_IN_MEMORY_AUTH_SECURITY = "1"
$env:HELLO_SERVICE_PERF_MODE = "1"
$env:HELLO_SERVICE_THREADS = "64"
$env:HELLO_SERVICE_BUSINESS_THREADS = "64"
$env:HELLO_SERVICE_MAX_INFLIGHT_REQUESTS = "16384"
$env:HELLO_SERVICE_MAX_PENDING_BUSINESS_TASKS = "8192"
```

说明：

- `IN_MEMORY_SESSIONS=1`：登录 Session 不写 Redis，进程重启后 token 失效。
- `IN_MEMORY_AUTH_SECURITY=1`：黑名单、验证码和登录风控不写 Redis，只适合单进程本机压测。
- `PERF_MODE=1`：关闭请求级 tracing、指标和普通日志，避免观测系统成为测试瓶颈。
- 生产环境必须关闭这三个开关，不能把本机极限数据当成多实例生产容量。

本机真实 MySQL + Redis 账号查询、内存 Session/风控的测试结果：

- `10000` 次登录，`128` 并发
- 平均吞吐约 `10663 登录/秒`
- 成功率 `100%`
- P99 约 `114.72ms`

注册不能直接按同一目标衡量。注册每次都必须执行密码哈希、账号写入和角色初始化；如果为了达到 `10000/s` 降低 Argon2/PBKDF2 成本，会直接降低密码安全性。注册应单独按 CPU 核数、哈希参数和可接受延迟压测。

## 2026-09-29 注册热路径回归

本次优化内容：

- 注册成功后的最后登录时间/IP改为复用登录审计的有界异步队列，队列满时同步回退。
- 注册新账号使用多端会话语义，不再执行没有意义的旧会话清理。
- 注册不再执行 `UPDATE account` 后再次 `SELECT account`，直接复用内存中的账号对象。
- 保留原有注册响应结构，UE 仍可读取 `account`、`player`、`session`。

本机内存仓储基线，安全密码哈希参数保持默认值：

- `100` 次唯一注册，`32` 并发，`100/100` 成功。
- 吞吐约 `172/s`，P50 `146.56ms`，P95 `304.59ms`，P99 `318.08ms`。
- `100` 个唯一账号登录回归，`100/100` 成功，吞吐约 `196/s`，P99 `261.62ms`。

这组数据的主要瓶颈是每个唯一账号必须独立执行密码哈希，而不是 HTTP 连接、Redis 或线程池。此前约 `10663/s` 的登录结果属于同一账号短期密码校验缓存命中场景，不能代表首次注册或大量不同账号登录。要让注册达到 `5000/s` 或 `10000/s`，应采用多进程/多机器横向扩展密码哈希 CPU，并保持正式哈希参数；不应通过关闭哈希、缓存失败结果或复用不同账号的哈希结果来换吞吐。

## 多进程注册压测

测试条件：本机 `14` 核、`20` 逻辑线程；内存仓储；正式密码哈希参数；`PERF_MODE=1`；每个进程 `4` 个业务线程；关闭仅针对无 token 注册请求的写请求串行化保护。每个进程监听独立端口，客户端把唯一注册账号均匀分发到各进程。

| 进程数 | 请求数 | 成功率 | 总吞吐 | P99 |
|---:|---:|---:|---:|---:|
| 1 | 800 | 100% | 100.64/s | 1724ms |
| 2 | 1600 | 100% | 187.49/s | 1684ms |
| 4 | 3200 | 100% | **237.62/s** | 934ms |
| 8 | 6400 | 100% | 219.39/s | 1573ms |

本机峰值出现在 `4` 个进程，约 `238/s`。增加到 `8` 个进程后吞吐下降并且尾延迟上升，说明密码哈希 CPU 已经饱和，继续增加进程不会线性扩展。要达到 `5000/s`，按这个实测规模粗略需要约 `21` 台同等 CPU 机器或等量 CPU 资源；达到 `10000/s` 约需 `42` 台，实际还要扣除数据库、网络、进程调度和安全风控开销。这不是 HTTP 层优化可以单独解决的问题。

## 认证保护配置

密码计算使用独立、有界线程池，避免注册/登录占满普通 HTTP 业务线程：

```powershell
$env:HELLO_SERVICE_PASSWORD_HASH_THREADS = "8"
$env:HELLO_SERVICE_PASSWORD_HASH_MAX_PENDING = "16"
```

当密码任务队列达到上限时，接口返回 HTTP `503` 和错误码 `password_queue_full`，而不是继续分配内存等待。默认队列上限为密码线程数的两倍。

注册限流默认按固定一分钟窗口执行：

```powershell
$env:HELLO_SERVICE_REGISTER_RATE_WINDOW_SECONDS = "60"
$env:HELLO_SERVICE_REGISTER_MAX_PER_LOGIN_IP = "3"
$env:HELLO_SERVICE_REGISTER_MAX_PER_IP = "30"
```

MySQL + Redis 模式使用 Redis Lua 脚本原子递增 `IP+登录名` 和 `IP` 两个计数，并只在窗口首次创建时设置 TTL，避免 `INCR` 与 `EXPIRE` 分离造成竞态。超限在密码哈希之前返回 HTTP `429`、错误码 `register_rate_limited`。内存仓储只适合单进程开发联调。

MySQL 注册账号写入使用单条 `INSERT IGNORE`，由 `account.login_name` 唯一索引处理并发重复注册，不再执行注册前的 `SELECT`。发生重复时根据 `affected_rows=0` 返回“登录名已存在”。这减少一次连接池借用和数据库往返，也避免“先查询后插入”的并发竞态。

## 2026-09-29 注册优化后回归

新增注册专用的 `PlayerRepository::create_for_registration()`：MySQL 注册时在一次连接租约内直接写入玩家主行和默认背包，并直接返回已知的默认资料，跳过登录兼容路径中的玩家查询、货币查询和背包查询。原有登录路径不变，内存仓储保持兼容实现。

本机内存仓储、正式密码哈希参数、密码哈希线程数 `10`：

- `400` 次唯一注册、并发 `32`：`187.90/s`，P99 `192.36ms`，成功率 `100%`。
- `400` 次唯一注册、并发 `64`：`183.61/s`，P99 `367.31ms`，成功率 `100%`。

并发从 `32` 提高到 `64` 后吞吐没有增加且 P99 翻倍，说明密码哈希 CPU 已经饱和。此次角色初始化和单次 INSERT 优化会主要体现在真实 MySQL 模式，不能从内存仓储基线推断具体倍数；需要启动本机 MySQL + Redis 后再做持久化实测。

## 2026-09-29 登录并发优化实现
